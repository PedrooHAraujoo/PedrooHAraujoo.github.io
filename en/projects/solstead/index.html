Context

An owner of rental homes in Central Florida needed one place for the tenant to request a repair, the owner to approve the quote and the vendor to log the job. Today that happens over messages and phone calls. The name is provisional and the demo only uses fictional data.

What I built

  • End-to-end maintenance requests: photos, quote, approval limit, scheduling and receipt.
  • Records for owners, properties, tenants, leases, listings and vendors, with email invitations.
  • Visit reports in PDF, statements in CSV and PDF, accounting ledger and monthly reconciliation.
  • Installable PWA with offline page and a public site with international SEO (hreflang, sitemap, structured data).
  • Demo mode that boots without credentials so the client can try every role.

Engineering decisions

  1. 01

    The database decides who sees what

    Every table has row-level control. The application only reaches the database through three doors (user, anonymous and system), and a missing resource answers exactly like a forbidden one, so nothing leaks.

  2. 02

    The demo runs production migrations

    Instead of in-memory fake data, the demo boots PostgreSQL inside the process (PGlite) with the same migrations. Identifiers are deterministic so it works in a serverless environment.

  3. 03

    Money in cents and immutable history

    Amounts are integer cents and ledger entries are never edited: mistakes are corrected with a reversal. The audit trail is hash-chained.

  4. 04

    Nothing simulated poses as real

    Anything not yet confirmed by the client stays null in configuration, and the build refuses to enter the production stage while something is incomplete.

How it was built

Built with Claude Code. Conventions are written in the repository (architecture, data model, launch checklist) and the test suite runs before every delivery; I define scope with the client and approve every release.
